# RTX 8000 matched 225K direct model result

Both direct `llama-bench` runs used the same Bonsai 2 27B PQ2 model, pinned upstream `adfffbe`, 225,000 prompt tokens, 128 generated tokens, Q8/Q8 KV, batch 4,096, microbatch 2,048, flash attention and one repetition. The custom run forced the committed CUTLASS prefill and PQ2/Q8 DP4A decode paths; the stock run used the original Bonsai CUDA library. The RTX 8000 production endpoint remained stock and unchanged. Robot `running_runs.total` was zero before each model load.

| Direct measurement | Stock Bonsai | Custom engine | Time reduction |
|---|---:|---:|---:|
| Prompt plus 128 generated tokens (`-pg 225000,128`) | 722.849 s | 589.975 s | **18.4%** |
| 128 generated tokens after a 225K cache fill (`-d 225000 -n 128`) | 10.390 s | 10.043 s | **3.3%** |

The second command performs the cache fill outside the timed generation section; its reported generation rates were 12.319 and 12.745 tokens/s, respectively. The prior 225K custom operation trace measured about 53.3 ms of attention in a 77.6 ms steady decode token, so attention limits the gain from the faster matrix kernels at this depth. These are one matched direct run per variant, not repeated-run distributions. `llama-bench` does not compare generated text or endpoint time-to-first-token.

The custom prompt-plus-generation dispatch log records 342 CUTLASS prefill and 347 DP4A decode selection events; the stock log records 689 Bonsai/Prism selections. These events prove path selection but do not count CUDA graph replays or total kernel launches. The requested CUDA operation profiler stopped after 128 graphs and was exhausted by `llama-bench`'s preliminary 512-prompt and 128-generation cases, before the 225K test. It cannot support a new 225K per-operation timing claim. The older 225K ten-token trace and its limitations are documented in [the attention report](rtx8000-attention-2026-10-06.md).
