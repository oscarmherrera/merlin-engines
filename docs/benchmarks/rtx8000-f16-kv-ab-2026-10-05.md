# RTX 8000 isolated F16-KV A/B — 2026-10-05

This tests a proposed decode-attention change, not a production configuration change. Two isolated `merlin-endpoint` processes ran **sequentially** on `.43:18081` with the pinned stock `prism-adfffbe` runtime and the same Bonsai 2 27B PQ2 model. The production stock endpoint on `:8081` stayed loaded and unchanged. The isolated processes used its 262,144-token context, four slots, batch 4,096, microbatch 2,048 and prefix-reuse setting. Only `--cache-type-k` and `--cache-type-v` changed from `q8_0/q8_0` to `f16/f16`. Robot `running_runs.total` was zero before each isolated load and request. Each process was stopped after its request, and device use returned to 18,552 MiB.

For each depth, both KV types received **identical request bytes**. The request was derived from the saved synthetic stock retrieval prompt, with the final instruction changed to request 200 numbered lines so a 128-token completion would measure decode. Prefix reuse was disabled for the request; temperature was zero and seed 12345. Both variants returned HTTP 200, `finish_reason=length`, all 128 output tokens and `[DONE]`. The response bytes matched between Q8 and F16 at each depth.

F16 reduced the server decode span by **20.8% at 61K** and **32.1% at 128K** in one pair at each depth. Whole-request wall fell **0.4% and 1.0%** respectively, while TTFT changed by +0.596 s and −0.895 s. Thus F16 is a measured decode improvement on these requests, but it does not deliver a meaningful long-context prefill or whole-request gain in this test. These single pairs have no run-to-run spread. The actual attention kernel name was not traced in these requests; the pinned source predicts a vector-to-MMA selection change for eligible Turing batch-1 requests, but this test establishes timing, not that mechanism.

After load, used device memory was **36,978 MiB for Q8** (11,425 MiB free) and **44,348 MiB for F16** (4,055 MiB free), with the production stock model co-resident. The +7,370 MiB is the observed **total device-use difference**, not a separately measured KV allocation. No model weights were changed. This modest remaining F16 headroom matters before testing deeper requests or concurrency.

The earlier stock 128K request generated only ten tokens and reported `decode_ms=2,123`, often summarized as 212 ms/token. The matched 128-token Q8 run here reported 7,095 ms, or 55 ms/token. These observations **refute 212 ms/token as a sustained rate**. A straight line through the two points has about 42 ms per additional token plus about 1.7 s fixed cost, but the runs occurred at different times with different output prompts; that intercept is a hypothesis, not an identified CUDA-graph, allocator or Go-loop cause. An endpoint operation trace would be needed to locate it. The prior proposal's sixfold DRAM-traffic estimate is also unproven: 7.8 GB of KV read six times at 672 GB/s implies a 69.6 ms lower bound, exceeding the previously measured 53.36 ms attention operation. Query-head references in source do not establish six DRAM fetches.
