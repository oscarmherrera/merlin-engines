# MTP speculative decoding for Bonsai 2 on the Prism runtime, 2026-10-08

Question (owner): can a multi-token-prediction head draft for Ternary Bonsai 2 27B, and what
does it buy on the Bonsai hosts? Bonsai 2 is derived from Qwen3.8-27B, which has a native
NextN block; PrismML ships no head and the deployed GGUF carries none. merlin-endpoint already
drafts with an MTP head (`--mtp-model`, live on ryzen since 2026-10-03), but on the Prism
fork that path refused: the fork lacks upstream's extended-batch API.

## What was built (scratch, nothing deployed)

- **Head file.** `Qwen3.8-27B-MTP-Q8_0.gguf` (Jackrong, Hugging Face; 29,047,084,352 B, SHA-256
  verified against the published `ab48c2f5…`) carries the base model's NextN block as `blk.64`.
  [`extract_mtp_head.py`](mtp-bonsai-2026-10-08-evidence/extract_mtp_head.py) writes the head-only
  file ggml-org's Flash-Next head has the shape of: `output`, `token_embd`, `output_norm` and
  `blk.64.*` (18 tensors, 3,164,006,720 B). The script rebuilt the Flash-Next head byte-identically
  as its self-test.
- **Runtime port.** [`prism-batch-ext-port.patch`](mtp-bonsai-2026-10-08-evidence/prism-batch-ext-port.patch)
  (317 lines on tag `prism-b10743-adfffbe`, generated by
  [`apply_batch_ext_prism.py`](mtp-bonsai-2026-10-08-evidence/apply_batch_ext_prism.py)) adds
  upstream llama.cpp's `llama_batch_ext_*` API and `llama_process` as a thin layer over the fork's
  own `llama_batch`: an entry carries a token id and the target's hidden-state row, one position per
  token (the fork's allocator broadcasts it across the rope sections), and `llama_process`
  materializes the old batch and calls `llama_decode`. That is exactly how the fork's own server
  feeds its draft head, so no graph code changes. Backend-independent: one `libllama` serves the
  Vulkan and CUDA hosts. Built on go-dev with `GGML_NATIVE=OFF`.
- **Not changed.** Bonsai 2 weights, the endpoint, every production unit. The earlier idea of
  giving the staging nextn functions C linkage was wrong and is not in the patch: the endpoint's
  binding looks those up by their mangled names on purpose.

## Endpoint production path, RTX 8000 (`.43`, CUDA), with the port

Same binary, same ported `libllama` beside the production CUDA Prism libraries, same flags
([`rtx8000-mtp-mtp.jsonl`](mtp-bonsai-2026-10-08-evidence/rtx8000-mtp-mtp.jsonl),
[`rtx8000-mtp-base.jsonl`](mtp-bonsai-2026-10-08-evidence/rtx8000-mtp-base.jsonl) and the
`rtx8000-mtp-mtp-{nograph,d1,d2}.jsonl` arms):

| Prompt | Base | MTP, draft max 3 | draft max 2 | draft max 1 | Acceptance (max 3 / max 1) |
| --- | ---: | ---: | ---: | ---: | ---: |
| warehouse filler, 8K | 39.49 | 44.17 (+12%) | 47.38 (+20%) | **48.84 (+24%)** | 51% / 71% |
| warehouse filler, 30K | 32.32 | 36.72 (+14%) | | | 49% |
| prose, short prompt | 42.14 | 40.68 (−3%) | 47.91 (+14%) | **51.22 (+21%)** | 42% / 66% |
| Go code, short prompt | 42.17 | **62.31 (+48%)** | 61.67 (+46%) | 59.84 (+42%) | 82% / 94% |

Acceptance per draft is the same as on the R9700, so the head is not the difference; the
per-step cost is. Each step is one verify decode on the target plus one replay decode and up to
three one-token decodes on the draft context, and on this card each extra decode call costs
about 5 ms of fixed time, against a 25 ms base token; on the R9700 the same call costs about
3 ms against a 34 ms base token. Disabling CUDA graphs (`GGML_CUDA_DISABLE_GRAPHS=1`) changed
nothing (43.61 / 40.70 / 62.18 tok/s), so the cost is not graph capture. Where the fixed
cost sits (the fork's per-decode graph build and allocation, the recurrent-state rollback on a
rejected draft, or the embedding read-backs) was not profiled.

## What to expect per host, and what is left

- **R9700 (Vulkan):** +39% at 30K depth, +80 to +93% on short prompts, +171% on code, at
  draft max 3. Measured on the production path.
- **RTX 8000 (CUDA):** +21 to +24% on general text at draft max 1, +42 to +48% on code. Measured.
  Draft max 1 is the right production setting on this card until the per-call cost is cut.
- **RTX 3090 (CUDA):** not measured; its 24 GB cannot hold the production endpoint and a second
  instance. Same runtime path as the RTX 8000, with a faster base decode, so expect the RTX 8000's
  range or a little less at draft max 1. Needs its own read, and a VRAM check for the 3.2 GB head
  (1.7 GB at Q4_0) beside its 81,920-token window.
- **P40 (CUDA, judge pool):** not measured. Its base decode is the slowest in the fleet, which
  is the regime where the fixed cost hides, so the R9700-like range is plausible; a verify batch
  of four on Pascal is the unknown.
- **Ryzen:** already drafting on its upstream build.

The port is 317 lines against the fork and is backend-independent; it belongs in PrismML's fork
(or disappears on a rebase onto current upstream, which has the API). To ship: the fork change,
the head file beside each host's weights, `--mtp-model` and `--mtp-draft-max` in each unit as
ryzen's already does, a per-host read of `mtp_accepted/mtp_drafted` and decode on the first run,
and the fixed-cost profile on CUDA, which is the lever that would bring the CUDA hosts up to the
R9700's ratios.
