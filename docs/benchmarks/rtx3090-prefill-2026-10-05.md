# RTX 3090 direct PQ2 prefill, 2026-10-05

This is a direct `test-backend-ops` operator comparison on the RTX 3090 (SM86,
24 GB). It is not a full-model or long-context result. The endpoint remained on
stock Bonsai. The custom path was forced without calibration; an unmatched
profile selected stock Bonsai in the same staged binary, with 256 Prism and no
CUTLASS selections in the [stock dispatch log](rtx3090-prefill-2026-10-05-evidence/merlin-prefill-sm86-rect-stock-kernel.log).
The perf harness repeats `MUL_MAT` nodes in one graph and reports
`ggml_backend_graph_compute` wall time divided by node runs. These values
include quantization and graph execution, rather than an isolated matrix kernel.

| PQ2 × F32 shape (M × N × K) | Custom 64×128×128 CUTLASS | Stock Bonsai | Custom vs stock |
| --- | ---: | ---: | ---: |
| 17408 × 2048 × 5120 | 3.656 ms | 3.372 ms | 8.4% slower |
| 5120 × 2048 × 17408 | 3.942 ms | 3.453 ms | 14.2% slower |

Both custom shapes passed direct CPU-reference correctness. The custom kernel
uses Bonsai's PQ2/Q8 arithmetic with a non-saturating CUTLASS SM86
`m16n8k32` integer MMA specialization. Nsight Compute confirms the same
44,564,480 executed `IMMA.16832` instructions as Bonsai on the first shape.
The dispatch candidate retains its original 128×128 label; the profiler's
kernel template identifies the actual 64×128 launch. That label must be fixed
before this candidate is shipped.
The initial 128×128 eight-warp candidate used 255 registers and incurred
78,753,792 local-load sectors. The 64×128 tile eliminated local loads and used
105 registers, but still executed 36,243,456 integer address instructions
versus 11,001,856 in stock, and requested 147,882,348 global-load sectors
versus 122,232,993. These are kernel-profile counters, not a decomposition of
the graph-per-node latency. A minimal single-metric profile measured the first
custom matrix kernel at 3.933 ms and stock at 3.937 ms. That profile cannot
explain the slower full graph result by itself.

A scratch-only benchmark harness capped the graph at 16 repeated nodes. The
first shape still took 3.614 ms per node custom versus 3.321 ms stock, a
0.293 ms gap; the original 166-node graph gap was 0.283 ms. Graph length did
not account for it. A minimal profile of the identical Q8 quantizer measured
65.152 µs custom and 65.120 µs stock. This also does not account for the gap.
The remaining discrepancy between profiled single-kernel time and direct graph
time was resolved by profiling a later launch in the repeated graph with cache
and clock controls disabled. That matrix kernel took 3.197 ms custom versus
2.931 ms stock, a 0.266 ms gap close to the direct 16-node gap of 0.293 ms.
The slowdown is in the matrix kernel rather than the shared Q8 quantizer.
On that launch, custom had 132.1 million L1 global-load miss sectors versus
61.2 million stock, and long-scoreboard stalls were 23.0% versus 8.4%.
DRAM reads were similar (356.5 versus 346.5 MB), while integer thread
instructions were 4.01 versus 2.88 billion. These counters identify excess
on-chip load waiting and address work; they do not prove which source operand
accounts for each miss. No SM86 speedup is claimed.

The stage originally contained three regular copies of `libggml-cuda`. The
test executable loads `.so.0`; copying only `.so.0.21.0` left the old kernel
active. Measurements attributed to the first SM86 MMA rebuild were discarded.
All three library names were updated before the results above.

The 64×64 tile reduced spills but took 4.018 ms on the first shape. A
128×128/16-warp tile either exceeded launch resources or took 4.418 ms with
register bounds. A 128×64 tile and 8-byte Q8 loads on the 64×128 tile were
correct but slower. Those experiments were removed from the retained source.
The SM86 candidate remains uncommitted while it loses to stock Bonsai.

Further isolated SM86 trials, each compared to the prior 64×128 custom result
above, also failed to close the gap:

| Trial | First shape | Second shape | Finding |
| --- | ---: | ---: | --- |
| Row-fast block order | 3.783 ms | 3.957 ms | L1 misses fell only 0.6%; long-scoreboard stalls rose to 27.3% |
| `const __restrict__` loads | 3.669 ms | 3.941 ms | Produced Bonsai's `LDG.E.U16.CONSTANT` form, without a timing gain |
| 128×128, 4×4 warps, register bound | 4.422 ms | 4.689 ms | The unbounded version could not launch; the bounded version passed correctness but lost |
| 64×128×64, two stages | 4.837 ms | 4.900 ms | Passed correctness but lost; 128-wide K with two stages exceeded static shared-memory limit at compile time |
| One-K-tile-ahead packed-weight prefetch | 3.663 ms | 3.859 ms | Passed correctness; first shape tied prior custom and second improved 2.1%, but both still lost to stock |

The losing edits were removed from the local candidate. The direct test
library on `.42` remains isolated from the production endpoint, which still
runs stock Bonsai. P40 optimization is deferred until the 3090 goal is met.

## Native Bonsai MMQ trials (isolated, not retained)

The 3090 candidate next moved to Bonsai's native packed-PQ2/Q8 MMQ to test
whether its existing integer Tensor Core path beat the SM86 CUTLASS kernel.
In a scratch build on `.30`, enabling Bonsai's existing Q8 `cp.async` double
buffer for SM86 PQ2 passed both direct CPU-reference cases. The same `.42`
test binary, two-shape input, and 16-node graph timing with engine logging
disabled gave the following matched results (microseconds per graph node):

| Shape (M × N × K) | Stock Bonsai MMQ | SM86 async MMQ | Change |
| --- | ---: | ---: | ---: |
| 17408 × 2048 × 5120 | 3339.16 | 3147.62 | 5.7% faster |
| 5120 × 2048 × 17408 | 3422.99 | 3248.48 | 5.1% faster |

The correctness-mode kernel log reported Prism dispatch for both shapes, so
the old custom CUTLASS kernel was not selected. Disabling stream-K on top of
the async change also passed correctness, but measured 3219.62/3291.65 µs,
worse than the async-only candidate.

A 256-row × 64-column MMQ tile first failed both correctness cases because
the unchanged 256-thread MMA writeback covered only 128 output rows. With 512
threads, both cases passed, but timing worsened to 3733.67/3789.79 µs versus
the same stock control. The larger tile is discarded. The 3090 prefill target
of at least 10% faster than stock on **both** shapes remains unmet. All MMQ
changes and libraries are scratch-only and isolated from the endpoint.

The RTX 8000 uses SM75; NVIDIA's `cp.async` requires SM80 or later. Therefore
the measured async part of this 3090 trial cannot be moved to the RTX 8000.
Its committed CUTLASS prefill remains the measured direct-operator winner on
that card; a Turing-safe MMQ alternative would need its own matched test.

The follow-up Nsight Compute profile of the **async-only** 3090 MMQ kernel
sampled its largest long-scoreboard stalls at two `PRMT` unpack instructions
(22,710 and 15,432 samples) immediately after a sequence of packed-weight
`LDG.E.U16.CONSTANT` loads. The profiled kernel read 346.7 MB from DRAM and
requested 122.7 million global-load sectors, close to the earlier stock
profile's 346.5 MB and 122.2 million sectors. These are separate profile
runs with uncontrolled clocks and caches; the source attribution identifies
a candidate bottleneck, not a projected speedup.

To test that bottleneck directly, a scratch SM86-only branch added one-tile-
ahead L1 hints for packed PQ2 weights inside Bonsai's async MMQ loop. Both
CPU-reference cases passed. With the same 16-node direct graph setup it ran
3127.12/3226.13 µs per node, versus async-only 3147.62/3248.48 µs and
stock 3339.16/3422.99 µs. The roughly 0.02 ms gain over async-only is one
measurement per variant and too small to treat as a reliable improvement.
It leaves the observed gap to stock at 6.4%/5.8%, below the 10% goal. The
prefetch experiment is staged only at
`/home/oscar/merlin-engine-stage-mmq-sm86-pq2-prefetch` on `.42`; no engine
code or endpoint changed. Work paused here for reassessment.
